# Patient workflows and LAN security review — 2026-09-08

## Scope and conclusion

Reviewed repository baseline `4715dc34db82e5c649230373224352299a727118` and implemented changes on `codex/patient-workflows-security-audit`. The reported patient gender-edit failure was reproduced: the form submitted read-only response fields that the strict API rejected. A second backend defect erased fields omitted from updates. Both are fixed. Appointment creation already had a server-search picker; this review repaired selection validation, reopening, error recovery and keyboard behavior, and extended exact-ID searching instead of introducing a second lookup mechanism.

The review also covered authentication, role enforcement, patient/encounter associations, scheduling concurrency, financial transactions/retries, uploads/downloads, transcription execution, SSE/public display, SQLite integrity, backup/restore, dependencies and network defaults. Confirmed issues and verification are below. This is a code and automated regression review, not a penetration-test certification, a clinical validation, or proof that every bug/vulnerability has been found. No live patient database or deployed clinic network was accessed. No production migration/deployment was performed.

Severity describes the consequence in a networked clinic; prerequisites such as an authenticated doctor account or local filesystem access matter.

## Schema, API and compatibility changes

Migration `internal/database/migrations/017_integrity_guards.sql` runs automatically on startup and preserves existing patient/clinical/financial records. It adds scheduling/clinical/account triggers, a login index, `idempotency_records`, `invoice_return_items`, `backup_status`, and `backup_records.assets_checksum`, and removes the old transcription command value. No destructive data reset or production migration was run here.

Patient `PUT` and new `PATCH` preserve omitted values and require a version. The existing frontend submits an editable whitelist. Missing record, malformed request, invalid value and stale version remain distinct errors. Appointment validation is stricter; pre-existing overlaps are not silently rescheduled. Existing clients without idempotency headers still work but lack retry guarantees. Legacy backups remain database-only. New backups must keep `.db` and `.db.files` together. All users must sign in after restore. Transcription installations must configure the OS environment variable.

Legacy invoice returns require staff stock review before further automatic restocking because prior data does not reliably identify returned line IDs. An ordinary financial refund without restocking remains available. Amounts and totals are limited to the exact JavaScript integer range.

Before upgrading, preserve a complete stopped copy of the current data root. Rehearse migration and rollback on an isolated copy. See [deployment and recovery](DEPLOYMENT.md) and [API contract](API.md).

## Remaining risks and release work

- The actual LAN, firewall, Windows ACLs, endpoint protection, TLS trust, installed viewers and backup storage were not available for inspection. Restrict network access, use a standard account, patch devices, and perform the target-device acceptance procedure before production rollout.
- Ransomware running with the application's OS permissions can alter its live data and continuously writable backups. Maintain a separately administered offline/immutable copy and test restoration onto a clean host. The app itself neither encrypts backups nor makes them immutable.
- No antivirus/content sandbox is bundled. DOC/DOCX/PDF/audio parsers and any administrator-installed transcription tool remain attack surfaces on clients or the host. Scan files and restrict macros/tools. Checksums and file signatures do not certify harmless content.
- Restore is validated and staged, but an OS/storage failure during multiple database/directory renames can require manual recovery. Keep pre-restore files, use a UPS, rehearse full recovery and measure actual disk-space/time needs. No power-failure simulation or destructive ransomware simulation was performed.
- Idempotency is implemented for invoice/POS/payment/refund writes. Browser pending keys are in memory, so a reload/new login after a lost response requires checking the ledger before submitting again. Other create endpoints (including insurance payments and expenses) still need deliberate operator retry handling.
- All doctor accounts have broad administrative privileges; there is no separate security-admin role or built-in MFA in this change. Named accounts, credential hygiene and restricted network/OS access remain necessary. Public display must be privacy-reviewed by the clinic.
- Dependency scans report known advisories only. The unused OpenPGP module advisory is retained transparently; no assertion of “zero vulnerabilities” or “ransomware-proof” is made. Monitor CI/dependency updates and commission an independent network/application penetration test before broad deployment.
- Complete browser CI and Windows/mobile smoke tests (patient editing/search/reschedule, expired-session SSE, reconnect, printing, uploads, installer upgrade and restore). The branch is intended for review; production deployment and native release acceptance remain separate steps.
